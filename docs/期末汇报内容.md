## 三、系统设计

### 3.1 总体架构

系统采用三层架构，自上而下为界面层、数据仓库层、数据层：

```
┌──────────────────── 界面层 ────────────────────┐
│ 首页 / 榜单 / 我的（Fragment）                  │
│ 地图页 / 详情页 / 登录页（Activity）            │
│ 各列表 Adapter                                  │
└───────────────────────┬────────────────────────┘
                        │ suspend 函数 / 回调
┌───────────────────────▼────────────────────────┐
│           数据仓库层（ToiletRepository）        │
│ 定位 → 逆地理 → POI 检索 → 排序 → 缓存 → 聚合   │
└───────────────────────┬────────────────────────┘
                        │
┌───────────────────────▼────────────────────────┐
│  数据层：Room 数据库 + 高德 SDK + SharedPreferences │
└────────────────────────────────────────────────┘
```

**设计要点：**

- 界面层只负责展示与交互，不直接访问数据库或网络；
- 数据仓库层封装完整数据流水线，是首页、地图页、榜单页的**统一数据出口**，保证多页面数据一致；
- 数据层负责持久化与外部服务调用。

### 3.2 页面结构

| 页面 | 类型 | 主要功能 |
|---|---|---|
| 首页 | Fragment | 定位城市、搜索入口、快捷入口、厕所信息流 |
| 榜单页 | Fragment | 好评榜、热评榜 |
| 我的页 | Fragment | 账号信息、我的评价、演示数据入口 |
| 地图页 | Activity | 全屏地图、蓝点定位、Marker 标注 |
| 详情页 | Activity | 头图、基础信息、指标卡、评价列表、导航按钮 |
| 登录页 | Activity | 登录 / 注册双模式 |

底部导航采用三个主 Tab（首页 / 榜单 / 我的），地图页与详情页通过 Intent 跳转。

### 3.3 核心业务流程

```
启动 App
   ↓
读取本地缓存，优先展示上次结果（秒开）
   ↓
申请定位权限 → 混合定位获取经纬度
   ↓
逆地理编码补全城市区名
   ↓
3km 圆形检索"公共厕所"
   ↓
转换为业务对象 → 计算球面距离 → 升序排序
   ↓
写入数据库缓存 + JOIN 聚合评价统计
   ↓
列表 / 地图 Marker 刷新
   ↓
点击进入详情 → 查看指标与评价 → 发布评价 / 一键导航
```

### 4.1 数据模型

数据库采用 Room 框架，当前版本 v3，包含三张表：

**users（用户表）**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER | 主键，自增 |
| username | TEXT | 用户名，唯一索引 |
| passwordHash | TEXT | 密码哈希值 |
| salt | TEXT | 随机盐值 |
| nickname | TEXT | 昵称 |
| createdAt | INTEGER | 注册时间 |

**toilets（厕所表）**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | TEXT | 主键，复用高德 POI 唯一标识 |
| name | TEXT | 名称 |
| address | TEXT | 地址 |
| lat / lng | REAL | 经纬度 |
| createdAt | INTEGER | 入库时间 |

**reviews（评价表）**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER | 主键，自增 |
| toiletId | TEXT | 外键，关联厕所 |
| userId | INTEGER | 外键，关联用户 |
| userName | TEXT | 发布者昵称 |
| rating | INTEGER | 星级 1~5 |
| content | TEXT | 评价内容 |
| tags | TEXT | 标签，逗号分隔 |
| paperStatus | INTEGER | 厕纸情况指标 |
| sinkType | INTEGER | 洗手台类型指标 |
| cleaned | INTEGER | 清理除味指标 |
| createdAt | INTEGER | 发布时间 |

### 4.2 表间关系

```
users 1 ──────< N reviews N >────── 1 toilets
```

- 一个用户可以发布多条评价；
- 一个厕所有多条评价；
- 评价通过 toiletId 与 userId 两个外键分别关联厕所与用户。

### 4.3 设计合理性

1. **主键复用**：厕所表主键直接采用高德 POI 的 uid，地图点位与数据库记录一一对应，避免重复入库。
2. **避免 N+1 查询**：列表页通过 LEFT JOIN + GROUP BY 聚合，一次查询同时取回厕所信息、平均分和评价数，而不是逐条查询。
3. **两级存储**：结构化数据进数据库，登录态、最近定位、搜索历史等轻量数据进 SharedPreferences 文件，各取所长。
4. **安全存储**：密码采用"随机盐 + 哈希"方式存储，数据库中不保存明文密码。

### 4.4 版本演进

| 版本 | 变更内容 |
|---|---|
| v1 | 建立厕所表与评价表 |
| v2 | 新增用户表，评价增加用户关联与标签 |
| v3 | 评价表新增厕纸、洗手台、清理三项指标 |

## 五、核心功能实现

### 5.1 定位与周边搜索

实现流程共六步：

1. **隐私合规声明**：在初始化地图 SDK 前完成隐私政策展示与同意声明，否则会出现定位失败、地图白屏；
2. **混合定位**：融合 GPS、Wi-Fi、基站三种信号获取经纬度，精度约 30 米；
3. **逆地理编码**：当定位返回的城市字段为空时，用经纬度反向查询行政区划，补齐城市区名；
4. **POI 圆形检索**：以用户位置为圆心、3 公里为半径，检索关键词"公共厕所"；
5. **距离重算与排序**：对每条结果重新计算球面距离并升序排列；
6. **缓存与聚合**：结果写入数据库，并通过聚合查询补充评价统计。

### 5.2 距离排序算法

**为什么不用地图默认排序？**

地图平台默认按 POI 权重排序，权重考虑了热度、等级等因素，但并不等于"离用户近"。本项目对结果重新计算真实距离，让"附近"名副其实。

**为什么用球面距离而不是平面距离？**

地球近似球体，经线长度随纬度变化，直接使用平面勾股定理计算经纬度距离，在城市尺度上会产生米级以上的误差。本项目采用 Haversine 公式计算两点间的球面距离：

```
a = sin²(Δφ/2) + cosφ₁ · cosφ₂ · sin²(Δλ/2)
d = 2R · atan2(√a, √(1−a))
```

其中 φ 为纬度、λ 为经度、R 为地球半径。该公式在几公里范围内的相对误差小于 0.5%，兼顾了精度与计算效率。

### 5.3 地图展示

- 使用定位图层实时显示用户蓝点，定位间隔 2 秒；
- 对每个检索结果在地图上添加 Marker；
- 建立 Marker 与厕所标识的双向映射，点击 Marker 可直达对应详情页；
- 定位成功后自动移动镜头到用户位置。

### 5.4 结构化指标卡

这是本项目在产品层面的特色功能。借鉴购房类应用展示房源关键指标的做法，本项目为公共厕所设计了三个结构化指标：

| 指标 | 取值 |
|---|---|
| 厕纸供应 | 没纸 / 偶尔有 / 充足 |
| 洗手台 | 无 / 公共 / 独立 |
| 清理除味 | 无专人 / 有专人 |

指标卡分两行展示：

- **结论行**：取最新一条评价的指标，反映最新使用者的真实反馈；
- **统计行**：显示所有填写者中各项的占比，例如"12/15 人表示有纸"，避免单条评价的偶然性。

用户发布评价时通过单选控件录入，默认已选，填写成本低；数据来源全部为用户评价，无需接入官方数据。

### 5.5 评价与榜单

**发布评价**：需登录后操作，一条评价包含星级、文字内容、多个标签以及三项指标。

**标签体系**：纸巾充足、干净卫生、免费、好找、不用排队等，详情页统计出现次数最多的标签，形成"大家都在说"板块。

**榜单算法**：

- 好评榜：按平均分降序排列，分数相同时评价数多者优先；
- 热评榜：按评价条数降序排列，反映数据热度；
- 前三名显示金、银、铜奖牌标识；
- 榜单与首页使用同一数据源，发布评价后实时变化。

### 5.6 用户体系

- 注册时校验用户名唯一性，用户名重复或密码过短会被拒绝；
- 登录成功后保存登录状态，未登录用户发布评价时自动引导登录；
- 密码处理：为每个用户随机生成 16 字节盐值，将盐值与密码拼接后进行哈希运算，数据库只保存哈希结果。

**为什么这样存密码？**

如果直接保存明文，数据库一旦泄露，用户密码会立即暴露；如果只做简单哈希，攻击者可以用预先计算的彩虹表反推常见密码。加入随机盐后，相同密码在不同用户处得到的哈希值不同，彩虹表失效。

> 说明：SHA-256 属于快速哈希，生产环境建议使用 BCrypt、Argon2 等专用慢哈希算法，本项目在报告中如实说明这一局限。

### 5.7 步行导航

- 通过隐式 Intent 匹配高德地图的导航协议，直接唤起步行导航；
- 当设备未安装高德地图时，捕获异常并自动回退到网页版导航；
- 该方案无需引入重量级导航 SDK，包体小，且覆盖所有机型。

## 六、关键技术原理分析

> 本章为技术深度补充内容，用于答辩时说明"不只是会调用框架，也理解其原理"。

### 6.1 混合定位原理

移动设备定位主要依靠三种信号：

- **GPS / 卫星定位**：室外精度可达 5~10 米，但室内信号弱、首次定位慢；
- **Wi-Fi 定位**：通过扫描到的 Wi-Fi 热点指纹与数据库比对，室内精度约 20~50 米；
- **基站定位**：根据手机连接的基站信息估算位置，精度较粗但覆盖广、速度快。

高德定位 SDK 将三种信号融合，根据当前环境自动选择或加权，兼顾速度与精度。

### 6.2 POI 检索与空间索引

POI（Point of Interest，兴趣点）检索的难点在于"如何在海量点位中快速找出某点附近的记录"。直接遍历全部数据显然不可行。

常见做法是先将二维经纬度编码为一维字符串（如 GeoHash），使空间上相邻的点具有相同前缀，再借助 B+ 树等索引结构进行范围查询。这样，圆形范围内的检索可以在毫秒级完成。

### 6.3 球面距离计算

Haversine 公式把经纬度看作球面上的角度，通过半正矢函数计算两点间的球面弧长。相比平面距离公式，它考虑了经线随纬度收敛的问题；相比考虑地球椭率的算法，它计算量更小。对于几公里范围的周边检索，它是精度与效率的平衡点。

### 6.4 地图瓦片渲染原理

地图并非一次性绘制全部内容，而是采用"瓦片金字塔"结构：第 1 层是一张覆盖全球的图，每提高一层，瓦片数量变为上一层的 4 倍，分辨率翻倍。客户端根据当前视口和缩放级别，只请求并拼接所需的若干张瓦片。这样既保证清晰度，又避免传输和渲染过量数据。

### 6.5 坐标系差异

- **WGS-84**：GPS 原始坐标，国际通用；
- **GCJ-02**：国内地图服务使用的加密坐标，俗称"火星坐标"。

如果在国内地图上直接使用 GPS 原始坐标，会出现数百米的偏移。高德 SDK 内部已处理该转换，因此开发者使用其输出坐标即可保证点位准确。

### 6.6 Room 的编译期校验

Room 是 Google 官方提供的 ORM 框架。开发者用注解声明实体与查询，编译阶段由注解处理器检查 SQL 语句中的表名、字段名是否与实体一致，一旦写错会直接编译失败，而不是等到运行时才报错；同时自动生成数据库实现代码，省去手写游标解析的样板代码。

### 6.7 跨应用通信

应用之间通过 Intent 通信。当应用发送一个带特定协议（scheme）的隐式 Intent 时，系统会查找注册了该协议的 App 并启动。如果设备上没有匹配的应用，系统会抛出异常，需要捕获后回退到其他方案（本项目回退到网页导航）。

## 八、开发过程中的问题与解决

### 8.1 依赖冲突

**问题**：高德地图、定位、搜索三个独立 SDK 包各自内嵌了相同的公共类，集成后编译期出现大量重复类错误。

**解决**：改用官方提供的三合一组合包，一次引入三项能力，版本号中同时包含各组件版本。

**结果**：构建成功，依赖数量下降。

### 8.2 城市信息为空

**问题**：在仅使用 GPS 定位的情况下，定位返回的城市字段为空，界面显示"位置未知"。

**解决**：定位成功后检测城市字段，为空时调用逆地理编码，将经纬度转换为行政区划信息。

**结果**：界面稳定显示"昆明市·呈贡区"。

### 8.3 列表查询效率低

**问题**：列表页为每一条厕所单独查询评价平均值，20 条结果需要发起 21 次查询，列表刷新明显卡顿。

**解决**：改写为一条聚合查询，通过连接与分组一次性取回全部统计信息。

**结果**：查询次数从 21 次降至 1 次，刷新流畅。

## 十一、项目特色与创新点

1. **指标结构化**：将"有没有纸、洗手台类型、是否有人清理"设计为三格指标卡，并展示众人统计结果，把购房类应用的决策辅助模式迁移到公共设施评价场景。
2. **真实距离排序**：不采用地图平台的默认权重排序，而是重新计算球面距离，"附近"更真实。
3. **无断点导航**：深链直达步行导航，未安装地图应用时自动回退网页版，覆盖所有机型。
4. **离线可用**：搜索结果落库缓存，冷启动优先展示本地数据，断网时仍可查看最近结果。

## 附录 B：答辩问答要点

**Q1：这个题目是不是太小、太简单？**

工具虽小，链路完整。项目覆盖了定位与地图、网络检索、数据库存储、多界面架构、用户体系和跨应用通信等主要知识点，每个环节都能讲清设计理由，比做大而空的平台更能体现工程能力。

**Q2：高德自己就能搜厕所，你们的差异在哪？**

三点差异：排序上，高德按平台权重，我们按真实球面距离；信息上，高德只有位置，我们补充了结构化指标和用户评价；流程上，从看到详情到导航是一步深链，不用反复切换。

**Q3：为什么用 Kotlin 而不是 Java？**

Kotlin 是 Google 官方首推语言，具备空安全、协程等特性，能在编译期减少空指针问题，异步代码更简洁，同等功能代码量更少。

**Q4：为什么用 Room 而不是直接操作 SQLite？**

Room 是官方 ORM 框架，SQL 在编译期校验，实体映射自动生成，省去大量手写代码，降低出错概率。

**Q5：为什么自己计算距离，而不是用地图返回的距离？**

地图返回的排序包含平台权重，不等于真实步行距离。我们重新计算球面距离，保证"附近"是按真实远近排列。

**Q6：Haversine 公式的原理是什么？**

它把经纬度视为球面角度，通过半正矢函数计算两点间的弧长。相比平面公式，它考虑了球面特性；相比椭球算法，它计算量更小，适合几公里范围的检索。

**Q7：密码是怎么存储的？**

每个用户生成随机盐值，将盐值与密码拼接后哈希，数据库只保存哈希结果。相同密码在不同用户处哈希值不同，可抵御彩虹表攻击。

**Q8：数据库为什么设计成三张表？**

对应厕所、评价、用户三类实体。评价通过两个外键分别关联厕所和用户，形成两条一对多关系，结构清晰、便于扩展。

**Q9：列表性能是怎么优化的？**

最初每条厕所单独查询评价统计，存在 N+1 问题。改为一条聚合查询后，查询次数从 21 次降到 1 次，列表刷新流畅。

**Q10：地图定位失败或白屏怎么处理？**

首先确保在使用地图前完成隐私合规声明；其次检查应用签名与地图 Key 的绑定关系；定位权限被拒绝时给出引导提示。

**Q11：步行导航是怎么实现的？**

通过隐式 Intent 匹配地图应用的导航协议直接唤起，若设备未安装对应应用则捕获异常，回退到网页版导航。

**Q12：演示数据是不是造假？**

不是。演示数据是标准的测试数据构造方式，用于展示榜单和指标在真实数据量下的效果。厕所点位来自地图真实检索，评价为测试数据，报告和代码中均有明确说明。

**Q13：项目完成度如何？**

核心功能已全部完成并在真机验证，界面经过重新设计，文档、测试记录等配套材料齐全。

**Q14：团队是如何协作的？**

使用 Git + GitHub 管理代码，任务通过 Issue 认领，功能在独立分支开发，经 Pull Request 评审后合并，提交信息统一规范。

**Q15：项目有什么创新点？**

指标结构化、真实距离排序、无断点导航、离线可用四点，既解决实际问题，也体现了设计思考。
