### 第 3 页 · 选题背景：出门在外，"方便"这件事不方便

四个痛点，每个痛点一句话：

1. **急用时找不到**：陌生街区、景区、夜间场景，地图搜索结果杂乱，混入商场内部点位与已关闭点位，试错成本高。
2. **好坏无从判断**：公共厕所普遍没有评价体系，有没有纸、干不干净、要不要排队全靠运气。
3. **信息不结构化**：厕纸供应、洗手台类型、是否有人清理等关键信息没有平台收录，无法提前决策。
4. **流程割裂**：从"搜到"到"走到"要在多个 App 之间反复跳转，急迫场景体验差。

- 配图建议：四个圆形序号 + 短句，避免大段文字。
- 讲解口径："找厕所是高频刚需，但市面工具要么搜不准、要么看不到好坏、要么导航要跳好几步。"

### 第 7 页 · 技术选型：成熟框架优先，不重复造轮子

| 层次 | 选型 | 版本 | 选型理由 |
|---|---|---|---|
| 开发语言 | Kotlin | 2.0.21 | Google 官方首选，空安全、协程、代码量更少 |
| 构建体系 | Gradle + AGP | 8.9 / 8.7.3 | 官方构建链，依赖走阿里云镜像加速 |
| UI 体系 | View + ViewBinding + Material 3 | 1.12.0 | XML 与设计稿一一对应、资料最全；Material 白送底部导航/卡片/弹窗 |
| 本地存储 | Room（SQLite ORM） | 2.6.1 | 编译期校验 SQL、KSP 生成实现类，三表 + JOIN 聚合 |

### 第 8 页 · 系统架构：三层分离 + 统一数据出口

| 层次 | 组成 | 职责 |
|---|---|---|
| 界面层 | HomeFragment / RankingFragment / MineFragment / MapActivity / ToiletDetailActivity / LoginActivity | 只负责展示与交互 |
| 数据仓库层 | `ToiletRepository`（单例数据流水线） | 定位 → 逆地理 → POI 检索 → Haversine 排序 → 缓存 → 聚合，首页 / 地图 / 榜单共用同一数据源 |
| 数据层 | Room 数据库（toilets / reviews / users）+ 高德 SDK + SharedPreferences | 持久化、外部服务、轻量键值 |

- Repository 模式的收益：换数据源只改一层；首页与地图结果永远一致；职责清晰，便于小组分工。
- 配图建议：三层堆叠方块 + 向下箭头。

### 第 9 页 · 数据库设计：Room 三表（v3）

| 表 | 作用 | 关键字段 |
|---|---|---|
| users | 本地账号 | id 主键、username 唯一索引、passwordHash + salt、nickname、createdAt |
| toilets | POI 缓存 | id 主键 = 高德 POI uid、name、address、lat、lng、createdAt |
| reviews | 用户评价 | id 主键、toiletId 外键 → toilets、userId 外键 → users、rating 1~5、content、tags、paperStatus / sinkType / cleaned |

- 合理性设计：
  - 结构化数据进 Room（查询 / 聚合 / 唯一约束），轻量会话数据进 SharedPreferences 文件，形成两级存储；
  - toilets 主键直接复用高德 POI uid，地图兴趣点与数据库记录一一对应；
  - 密码经 SHA-256(salt + pwd) 哈希落库，不存明文；
  - LEFT JOIN 一次查询同时取回厕所与均分 / 评价数，避免 N+1 查询。
- 配图建议：三张表 + 一对多连线（users 1:N reviews N:1 toilets）。

## 三、期中 Q&A 高频问题速答（详细版见 `期中开题答辩预案-附近厕所.docx`）

**选题价值类**

- 题目是不是太小？——工具虽小、链路完整，覆盖定位、网络检索、数据库、多界面架构、用户体系、跨应用通信。
- 高德自己就能搜厕所，差异在哪？——排序更真实（Haversine）、信息更结构化（三指标 + 评价）、流程更短（一步深链导航）。
- 谁来发评价？——短期演示数据生成器保底；中期靠"搜厕所的人天然是刚用过的人"沉淀；长期云端共享形成网络效应。

**技术实现类**

- 为什么 Kotlin 不用 Java？——空安全、协程、官方首选、代码量更少。
- 为什么 XML 不用 Compose？——与设计稿一一对应、Material 组件成熟、资料最多，课程场景更稳。
- Room 和 SQLite 区别？——编译期校验 SQL、自动映射实体、KSP 生成实现，省掉游标样板代码。
- 高德 Key 要钱吗？——个人认证免费，每接口每日约 5000 次配额，超出只失败不扣费。
- Haversine 是什么？——把经纬度当球面角距换算成弧长，几公里内误差小于 0.5%，精度与成本平衡。
- 密码怎么存？——每用户随机 16 字节盐 + SHA-256 哈希，不存明文；生产应换 BCrypt/Argon2。
- 数据库为什么三张表？——厕所、评价、用户三类实体，评价通过 toiletId / userId 两个外键关联。
- N+1 查询怎么解决？——列表原为每行单独查询，改写成一条 LEFT JOIN + GROUP BY 聚合，查询次数 21 → 1。
- 深链导航怎么做的？——隐式 Intent 匹配 `amapuri://`，未装高德捕获异常回退网页版。

**进度 / 分工 / 压力类**

- 现在完成多少？——约 85%，核心闭环真机跑通，剩余深色模式、收藏、README、测试记录。
- 小组怎么分工？——组长负责架构与核心功能，成员 B 负责深色模式与收藏，成员 C 负责文档与测试。
- 最大的困难？——三个高德独立包 Duplicate class 冲突，改用官方三合一组合包解决。
- 演示数据是不是作弊？——是标准测试数据构造工具；toilets 来自高德真实检索，评价为随机测试数据，报告已如实标注。

- 讲解口径：这一页是演示脚本，照着顺序操作即可。

### 第 4 页 · 核心实现 ①：定位与周边搜索的数据流水线

六步流水线：

| 步骤 | 说明 |
|---|---|
| 1 混合定位 | GPS / WiFi / 基站融合，精度约 30m |
| 2 逆地理编码 | city 为空时经纬度 → "昆明市·呈贡区" |
| 3 POI 圆形检索 | `SearchBound(圆心, 3000m)` 关键词"公共厕所" |
| 4 Haversine 排序 | 球面距离升序，误差 < 0.5% |
| 5 Room 缓存 | toilets 表按 uid 覆盖写入 |
| 6 JOIN 聚合 | 均分 + 评价数一条 SQL，防 N+1 |

- 为什么自己重算距离：高德默认排序按平台权重，与真实步行远近不一致；Haversine 公式 `a = sin²(Δφ/2) + cosφ1·cosφ2·sin²(Δλ/2)`，`d = 2R·atan2(√a, √(1−a))`。
- 代码位置：`util/DistanceUtil.kt`（Haversine）、`util/ToiletRepository.kt`（六步流水线单例）。
- 讲解口径：这是全项目技术含量最高的一页，讲清"为什么要自己算距离"。

### 第 5 页 · 核心实现 ②：点评式信息架构与厕所指标卡

- 界面设计原则（对应"界面设计 10 分"）：
  - 借鉴大众点评的信息架构，皮肤采用自有蓝绿品牌色系，评分星保留通用琥珀色；
  - 首页 = 渐变头部（定位城市 + 搜索）+ 金刚区三入口 + 四色信息流卡片，避免同色单调；
  - 详情页 = 头图与列表卡片同色联动（按 POI id 稳定哈希取色）+ 上叠式信息白卡；
  - 全程 ViewBinding + Material 3 组件：BottomNavigation / Chip / ToggleGroup / BottomSheet。
- 三格指标卡（购房软件式）：
  - 厕纸供应 / 洗手台 / 清理除味；
  - 结论行：取最近一条评价的指标（最新使用者反馈最真实）；
  - 统计行：x/y 人，所有填写者的占比，单人偏差被稀释；
  - 发布时 ToggleGroup 单选，默认已选，零成本填写；
  - 数据来源全部为用户评价（UGC），无需官方数据接入。
- 配图建议：首页信息流截图 + 详情页指标卡截图并排。

### 第 6 页 · 核心实现 ③：评价系统与实时榜单

- 评价数据模型（每条评价 = 11 个字段）：
  - 星级 1~5 + 文字内容 + 发布者（userId 外键）+ 时间戳；
  - 标签：纸巾充足 / 干净卫生 / 免费 / 好找 / 不用排队（多选，逗号入库）；
  - 指标三项：paperStatus / sinkType / cleaned（整型编码，-1 未填）。
- 实时榜单算法：
  - 好评榜：均分降序，同分按评价数多者优先；
  - 热评榜：评价条数降序（数据热度）；
  - 前三名金 / 银 / 铜奖牌；数据源与首页同源，发布即变。
- 登录体系（本地账号）：
  - 发布评价强制登录（未登录自动跳转登录页）；
  - users 表 username 唯一索引防重复注册；
  - 密码以 `SHA-256(salt + password)` 哈希落库，salt 每用户随机生成（SecureRandom 16 字节）。

### 第 7 页 · 系统架构：三层分离 + Repository 统一数据出口

| 层次 | 组成 | 职责 |
|---|---|---|
| 界面层 | HomeFragment / RankingFragment / MineFragment / MapActivity / ToiletDetailActivity / LoginActivity + 3 个 Adapter | 展示与交互，Fragment 宿主 + BottomNavigation |
| 数据仓库层 | `ToiletRepository`（object 单例） | 定位 → 逆地理 → POI → 排序 → 缓存 → 聚合的完整流水线；首页 / 地图 / 榜单共用 |
| 数据层 | Room（toilets / reviews / users v3）+ 高德 SDK 组合包 + SharedPreferences | 持久化、外部 LBS 服务、轻量键值 |

- 收益：更换数据源只改 Repository 一层；三条页面共用同一数据出口，杜绝不一致；职责边界清晰支撑小组并行开发。

### 第 8 页 · 数据存储设计：两级存储，各司其职（10 分考核点）

- Room 数据库 `toilet.db`（v3，结构化数据）：
  - toilets：POI 缓存，主键直接复用高德 POI uid；
  - reviews：评价 + 标签 + 三指标，toiletId / userId 双外键；
  - users：本地账号，username 唯一索引；
  - LEFT JOIN + GROUP BY + AVG / COUNT 聚合查询，一条 SQL 取回列表所需全部字段；
  - 编译期 SQL 校验：Room 在编译阶段检查字段与表名，错误不过夜。
- SharedPreferences 文件（轻量会话）：
  - 登录态：userId / username / nickname；
  - 最近定位：经纬度 + 城市区名；
  - 搜索历史：8 条上限、去重置顶；
  - 本质是 `/data/data/包名/shared_prefs/` 下的 XML 文件。
- 合理性论证：按数据特征选介质——需要查询 / 聚合 / 约束的进数据库，轻量键值进文件；密码加盐不落明文。
- 安全设计：SHA-256 + 每用户随机盐（SecureRandom 16 字节），彩虹表失效；正式版规划 Migration 与 SQLCipher。

### 第 9 页 · 地图定位实现：从"拿到坐标"到"走到门口"（10 分考核点）

六步：

1. **隐私合规**：`updatePrivacyShow` / `updatePrivacyAgree` 三 SDK 先行声明，否则定位错误码 12、地图白屏。
2. **蓝点图层**：MyLocationStyle 连续定位 2s 间隔，地图上实时蓝点。
3. **单点定位**：AMapLocationClient 拿经纬度 → 移动镜头 → 触发周边搜索。
4. **Marker 渲染**：逐点 addMarker，uid ↔ Marker 双向映射支持点选。
5. **深链导航**：`amapuri://route/plan` 直达高德步行导航。
6. **网页回退**：未装高德捕获异常回退 `uri.amap.com`，全机型可用。

- 代码位置：`ui/MapActivity.kt`、`ToiletApp.kt`、`ToiletDetailActivity.navigateOnFoot()`。

### 第 10 页 · 工程实践：三个真实踩坑与解决

| 问题 | 原因 | 解决 | 结果 |
|---|---|---|---|
| Duplicate class 冲突 | 三个独立高德包各自内嵌相同公共类，dex 合并失败 | 改用官方三合一组合包 `3dmap-location-search` | 构建成功，依赖数下降 |
| 定位成功但城市为空 | 纯 GPS 模式下 `AMapLocation.city` 返回空串 | 检测为空时调用 GeocodeSearch 逆地理编码补齐 | 稳定显示"昆明市·呈贡区" |
| 列表页 N+1 查询 | 逐条查询每间厕所的评价均值，20 条结果发起 21 次 SQL | 改写为 LEFT JOIN + GROUP BY 聚合查询 | 查询次数 21 → 1，刷新流畅 |

- 讲解口径：这是最能体现"真实开发过程"的一页，答辩时优先讲。
