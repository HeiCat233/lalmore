## 摘  要

随着移动互联网的发展，位置服务已深度融入日常生活，但"在外如何快速找到一处干净可用的公共厕所"这一高频刚需，仍未得到很好的解决。现有地图应用虽然能够搜索厕所点位，但存在排序不符合真实距离、缺乏质量信息、导航流程割裂等问题。

本文设计并实现了一款名为"附近厕所"的 Android 应用。应用基于 Kotlin 语言开发，采用高德地图 SDK 实现混合定位、周边检索、地图标注与步行导航，采用 Room 框架实现本地数据持久化，并设计了厕纸供应、洗手台类型、清理除味三项结构化指标与用户评价体系。系统采用界面层、数据仓库层、数据层三层架构，通过统一的数据仓库封装完整的"定位—检索—排序—缓存—聚合"数据流水线。

在关键技术方面，本文采用 Haversine 球面距离公式对检索结果重新排序，保证"附近"按真实距离排列；采用"随机盐 + 哈希"方式存储用户密码，避免明文泄露；通过聚合查询优化列表性能，将查询次数由 21 次降至 1 次。项目同时使用 Git 进行团队协同开发，建立了分支开发、Pull Request 评审与规范提交的协作流程。

测试结果表明，应用各项功能运行正常，在真机上完成了全流程验证，能够稳定满足课程考核要求与实际使用需求。

**关键词**：Android；Kotlin；高德地图；Room；位置服务；UGC 评价

## 1 项目概述

### 1.1 选题背景

"找厕所"是每个人都可能遇到的即时需求。在熟悉的区域内，这个问题通常不成为问题；但一旦身处陌生街区、旅游景区、大型商场或夜间环境，"如何快速找到一处可用、干净的公共厕所"就会变成一个真实的困扰。

通过对现有工具的使用与观察，可以发现几个普遍存在的问题：

1. **搜索结果不精准**。通用地图应用搜索"厕所"时，结果中常常混入商场内部点位、已关闭点位和名称相近的无关地点，用户需要逐个判断。
2. **排序不符合真实距离**。地图平台的搜索结果按综合权重排序，权重中包含了热度、等级等因素，导致"最近的"未必排在最前。
3. **缺少质量信息**。厕所有没有纸、洗手台是公共还是独立、是否有人定时清理，这些直接决定体验的信息，没有任何平台进行结构化收录。
4. **流程割裂**。从"搜到"到"走到"往往需要在地图、点评等多个应用之间切换，在急迫场景下体验较差。

### 1.2 项目目标

本项目旨在开发一款轻量的 Android 应用，让用户能够：

- **搜得到**：快速定位并找到附近真实可用的公共厕所；
- **看得懂**：通过结构化指标与用户评价，提前判断厕所的实际条件；
- **走得到**：从详情页一键唤起步行导航，直接走到目的地。

### 1.3 项目意义

从实用角度看，本应用解决了一个真实、高频、刚需的场景问题，具有一定的实用价值。

从课程角度看，本项目场景虽小但链路完整，覆盖了移动应用开发的主要知识点，包括：位置服务与地图、网络数据检索、本地数据持久化、多页面架构组织、用户账户体系、跨应用通信以及团队协同开发。

## 3 系统设计

### 3.1 设计原则

本项目遵循"使用成熟框架、不重复造轮子"的原则。地图与定位、数据持久化、界面组件等能力均采用成熟的官方或第三方框架，将开发精力集中在业务整合、数据处理与工程质量上。

### 3.2 技术选型

| 层次 | 技术 | 版本 | 选型理由 |
|---|---|---|---|
| 开发语言 | Kotlin | 2.0.21 | Google 官方首推，空安全、协程、语法简洁 |
| 构建系统 | Gradle + AGP | 8.9 / 8.7.3 | Android 官方构建体系，依赖管理方便 |
| 界面体系 | View + ViewBinding + Material 3 | 1.12.0 | 组件成熟、资料丰富，与设计稿对应直观 |
| 页面组织 | 单 Activity 宿主 + Fragment | — | 底部导航切换流畅，页面职责清晰 |
| 异步模型 | Kotlin 协程 | 1.8.1 | 数据库与网络操作不阻塞主线程 |
| 本地数据库 | Room | 2.6.1 | 官方 ORM，编译期校验 SQL |
| 地图能力 | 高德 Android SDK（组合包） | 11.3.x | 定位、地图、检索、逆地理一体化 |
| 轻量存储 | SharedPreferences | — | 保存登录态、最近定位等键值数据 |
| 密码安全 | SHA-256 + 随机盐 | — | 不存储明文密码 |
| 版本管理 | Git + GitHub | — | 满足团队协同考核要求 |

### 3.3 总体架构

系统采用三层架构：

```
┌──────────────────── 界面层 ────────────────────┐
│ 首页 / 榜单 / 我的（Fragment）                  │
│ 地图页 / 详情页 / 登录页（Activity）            │
│ 各列表 Adapter                                  │
└───────────────────────┬────────────────────────┘
                        │ suspend 函数 / 回调
┌───────────────────────▼────────────────────────┐
│           数据仓库层（ToiletRepository）        │
│ 定位 → 逆地理 → POI 检索 → 排序 → 缓存 → 聚合   │
└───────────────────────┬────────────────────────┘
                        │
┌───────────────────────▼────────────────────────┐
│ 数据层：Room 数据库 + 高德 SDK + SharedPreferences │
└────────────────────────────────────────────────┘
```

**各层职责：**

| 层次 | 职责 |
|---|---|
| 界面层 | 页面展示与用户交互，不直接访问数据库与网络 |
| 数据仓库层 | 封装完整数据流水线，作为所有页面的统一数据出口 |
| 数据层 | 数据持久化、外部服务调用、轻量键值存储 |

**架构收益：**

- 数据来源变更时只需修改仓库层，界面层无需改动；
- 首页、地图页、榜单页共用同一数据出口，保证数据一致；
- 各层职责边界清晰，便于小组分工与并行开发。

## 4 数据库设计

### 4.1 数据模型概述

数据库采用 Room 框架，当前版本为 v3，包含三张表：用户表、厕所表、评价表。此外，登录状态、最近定位、搜索历史等轻量数据使用 SharedPreferences 文件存储，形成"数据库 + 文件"两级存储结构。

### 4.2 表结构设计

**表 4-1 users（用户表）**

| 字段名 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | INTEGER | 主键，自增 | 用户编号 |
| username | TEXT | 唯一索引，非空 | 用户名 |
| passwordHash | TEXT | 非空 | 密码哈希值 |
| salt | TEXT | 非空 | 随机盐值 |
| nickname | TEXT | — | 昵称 |
| createdAt | INTEGER | — | 注册时间戳 |

**表 4-2 toilets（厕所表）**

| 字段名 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | TEXT | 主键 | 复用高德 POI 唯一标识 |
| name | TEXT | 非空 | 厕所名称 |
| address | TEXT | — | 详细地址 |
| lat | REAL | 非空 | 纬度 |
| lng | REAL | 非空 | 经度 |
| createdAt | INTEGER | — | 入库时间戳 |

**表 4-3 reviews（评价表）**

| 字段名 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | INTEGER | 主键，自增 | 评价编号 |
| toiletId | TEXT | 外键 → toilets.id | 所属厕所 |
| userId | INTEGER | 外键 → users.id | 发布用户 |
| userName | TEXT | — | 发布者昵称 |
| rating | INTEGER | 1~5 | 星级评分 |
| content | TEXT | — | 评价内容 |
| tags | TEXT | — | 标签，逗号分隔 |
| paperStatus | INTEGER | — | 厕纸指标编码 |
| sinkType | INTEGER | — | 洗手台指标编码 |
| cleaned | INTEGER | — | 清理除味指标编码 |
| createdAt | INTEGER | — | 发布时间戳 |

### 4.3 表间关系

```
users 1 ──────< N reviews N >────── 1 toilets
```

一个用户可以发布多条评价，一个厕所有多条评价，评价通过 toiletId 与 userId 两个外键分别关联厕所与用户。

### 4.4 指标字段编码

三项结构化指标采用整型编码存储，未填写时记为 -1：

| 指标 | 取值编码 |
|---|---|
| paperStatus（厕纸供应） | -1 未填 / 0 没纸 / 1 偶尔有 / 2 充足 |
| sinkType（洗手台） | -1 未填 / 0 无 / 1 公共 / 2 独立 |
| cleaned（清理除味） | -1 未填 / 0 无专人 / 1 有专人 |

### 4.5 数据库版本演进

| 版本 | 变更内容 |
|---|---|
| v1 | 建立厕所表与评价表 |
| v2 | 新增用户表；评价表增加用户关联与标签字段 |
| v3 | 评价表新增厕纸、洗手台、清理三项指标字段 |

> 说明：开发阶段采用破坏式迁移策略，正式上线前需编写完整的数据迁移方案，此点已列入改进计划。

### 4.6 设计合理性分析

1. **主键复用**。厕所表主键直接采用高德 POI 的唯一标识，地图点位与数据库记录一一对应，避免重复入库与数据不一致。
2. **避免 N+1 查询**。列表页通过连接与分组聚合，一次查询同时取回厕所信息、平均分和评价数，而不是为每条记录单独查询。
3. **按数据特征选择介质**。需要查询、聚合、约束的结构化数据存入数据库，轻量键值数据存入 SharedPreferences 文件，各取所长。
4. **安全存储**。密码采用"随机盐 + 哈希"方式，数据库不保存明文。

## 5 详细设计与实现

### 5.1 应用启动与初始化

应用启动时，在全局 Application 中完成三项初始化工作：

1. 完成高德地图、定位、搜索三个 SDK 的隐私合规声明；
2. 初始化 Room 数据库单例；
3. 初始化会话管理器。

其中隐私合规声明必须在地图相关功能使用之前完成，否则会出现定位失败、地图白屏等问题，这是本项目在开发中遇到的一个典型问题。

### 5.2 定位与周边搜索流程

完整的定位与搜索流程如下：

```
申请定位权限
   ↓
混合定位获取经纬度
   ↓
判断城市字段是否为空
   ↓（为空）
逆地理编码补齐城市区名
   ↓
3km 圆形检索"公共厕所"
   ↓
转换为业务对象
   ↓
计算球面距离并升序排序
   ↓
写入数据库缓存
   ↓
聚合评价统计
   ↓
刷新列表与地图 Marker
```

**（1）权限申请**

应用启动时动态申请定位权限，若用户拒绝，则给出提示引导，应用不崩溃，仍可浏览缓存数据。

**（2）混合定位**

调用定位客户端获取当前位置，同时配置蓝点图层用于地图上的实时位置展示，定位间隔设置为 2 秒。

**（3）逆地理编码兜底**

在仅使用 GPS 定位的情况下，定位结果中的城市字段可能为空。此时调用逆地理编码服务，将经纬度转换为行政区划信息，保证界面能够显示"城市·区县"。

**（4）周边检索**

以用户当前位置为圆心、3000 米为半径构造搜索范围，关键词设置为"公共厕所"。

### 5.3 距离计算与排序

**（1）问题分析**

地图平台返回的结果默认按综合权重排序，权重中包含热度、等级等因素，排序结果并不等于按距离排序。为了突出"附近"这一核心定位，本项目对结果重新计算真实距离并排序。

**（2）算法选择**

地球近似球体，经线长度随纬度升高而缩短。若直接使用平面勾股定理计算经纬度距离，在城市尺度上会产生米级以上的误差。因此本项目采用 Haversine 球面距离公式：

```
a = sin²(Δφ/2) + cosφ₁ · cosφ₂ · sin²(Δλ/2)
c = 2 · atan2(√a, √(1−a))
d = R · c
```

其中：

- φ 为纬度，λ 为经度，Δ 表示两点差值；
- R 为地球平均半径，取 6371000 米；
- d 为两点间的球面距离。

该公式在几公里范围内的相对误差小于 0.5%，兼顾了精度与计算效率。

**（3）实现方式**

对每条检索结果，计算其与用户当前位置的球面距离，然后按距离升序排列，列表卡片上同时显示距离值，便于用户直观判断。

### 5.4 地图展示与交互

**（1）蓝点定位**

通过定位图层在地图上显示用户当前位置的蓝点，并设置连续定位模式。

**（2）Marker 渲染**

对每条检索结果在地图上添加 Marker，标记公共厕所位置。

**（3）点选交互**

建立 Marker 与厕所标识的双向映射关系。用户点击某个 Marker 时，可以根据映射关系找到对应的厕所记录，跳转到详情页。

**（4）镜头控制**

定位成功后自动将地图镜头移动到用户位置，并设置合适的缩放级别，使周边厕所点位处于可视范围内。

### 5.5 厕所详情页

详情页由四个部分组成：

1. **头图区**：采用与列表卡片同源的颜色，保证视觉连续性；
2. **基础信息卡**：名称、地址、距离、评分；
3. **指标卡**：三项结构化指标，分为结论行与统计行；
4. **评价区**：标签统计与评价列表。

### 5.6 结构化指标卡设计

这是本项目在产品设计上的特色功能。

**（1）设计来源**

借鉴购房类应用展示房源关键指标的方式，将公共厕所最受关注的三个维度提取为结构化指标：

| 指标 | 说明 |
|---|---|
| 厕纸供应 | 是否有纸，是用户最关心的问题之一 |
| 洗手台 | 洗手设施是公共还是独立 |
| 清理除味 | 是否有专人定时清理 |

**（2）展示方式**

指标卡分为两行：

- **结论行**：展示最新一条评价对应的指标取值，反映最新使用者的真实反馈；
- **统计行**：展示所有填写者中各取值的占比，例如"12/15 人表示有纸"，避免单条评价的偶然性。

**（3）录入方式**

发布评价时，三项指标通过单选控件录入，默认已选中中间值，用户只需确认或微调，填写成本低。

**（4）数据来源**

指标数据全部来源于用户评价（UGC），无需接入官方数据源，既降低了数据获取成本，也使指标能够反映真实使用情况。

### 5.7 用户体系

**（1）注册**

注册时校验用户名唯一性，若用户名已存在则拒绝注册并提示；同时校验密码长度，过短则拒绝。

**（2）登录**

登录时根据用户名查询用户记录，将输入的密码与存储的盐值拼接后重新计算哈希，与数据库中的哈希值比对，一致则登录成功。

**（3）登录态保持**

登录成功后，将用户标识、用户名、昵称写入 SharedPreferences 文件，应用重启后仍保持登录状态。

**（4）密码安全**

为每个用户随机生成 16 字节盐值，采用"盐值 + 密码"拼接后哈希的方式存储。相同密码在不同用户处得到不同的哈希值，使彩虹表攻击失效。

### 5.8 评价发布

评价发布流程如下：

1. 判断登录状态，未登录则跳转登录页；
2. 弹出发布面板，包含星级、标签、三项指标与文字内容；
3. 校验内容是否为空；
4. 写入评价表；
5. 刷新详情页指标卡、标签统计与评价列表；
6. 榜单页数据同步更新。

### 5.9 排行榜

**（1）好评榜**

按厕所的平均评分降序排列，评分相同时评价数量多者优先。

**（2）热评榜**

按厕所的评价数量降序排列，反映数据热度。

**（3）展示效果**

榜单前三名分别显示金、银、铜奖牌标识。榜单与首页使用同一数据源，发布新评价后名次实时变化。

### 5.10 步行导航

**（1）深链唤起**

通过隐式 Intent 匹配高德地图的导航协议，携带目的地经纬度直接唤起步行导航。

**（2）异常回退**

当设备未安装高德地图时，系统会抛出异常。应用捕获该异常后，自动回退到网页版导航，保证所有机型都能正常使用导航功能。

### 5.11 演示数据生成

## 6 关键技术原理分析

本章对项目中使用到的关键技术原理进行分析，说明在调用框架的同时对其底层机制的理解。

### 6.1 混合定位原理

移动设备定位主要依赖三类信号：

| 定位方式 | 原理 | 精度 | 特点 |
|---|---|---|---|
| GPS / 卫星定位 | 接收多颗卫星信号，通过测距交会计算位置 | 室外 5~10 米 | 精度高，室内弱、首次定位慢 |
| Wi-Fi 定位 | 扫描周边 Wi-Fi 热点，与位置指纹库比对 | 室内 20~50 米 | 室内效果好 |
| 基站定位 | 根据连接的基站信息估算位置 | 百米级 | 覆盖广、速度快 |

定位 SDK 将三类信号融合，根据当前环境自动选择或加权计算，兼顾定位速度与精度。

### 6.2 POI 检索与空间索引

POI 检索的核心问题是：如何在海量点位中快速找出某一坐标附近的记录。若逐一计算距离，计算量无法接受。

常见解决方案是空间索引。以 GeoHash 为例，它将二维经纬度编码为一维字符串，使空间上相邻的点具有相同前缀，从而把二维范围查询转化为一维前缀查询，借助 B+ 树等索引结构即可实现毫秒级响应。此外还有 R 树等专门的空间索引结构。

### 6.3 球面距离计算

Haversine 公式把经纬度视为球面上的角度，通过半正矢函数计算两点间的球面弧长。与平面距离公式相比，它考虑了经线随纬度收敛的问题；与考虑地球椭率的算法相比，它的计算量更小。对于几公里范围的周边检索，它是精度与效率的平衡点。

### 6.4 地图瓦片渲染原理

地图并非一次性绘制全部内容，而是采用"瓦片金字塔"结构：

- 第 1 层是一张覆盖全球的地图；
- 每提高一层，瓦片数量变为上一层的 4 倍，分辨率翻倍；
- 客户端根据当前视口和缩放级别，只请求并拼接所需的若干张瓦片。

这种设计既保证清晰度，又避免传输和渲染过量数据。瓦片按 z/x/y 三级编号，z 表示层级，x、y 表示在该层中的行列位置。

### 6.5 坐标系差异

| 坐标系 | 说明 |
|---|---|
| WGS-84 | GPS 原始坐标，国际通用 |
| GCJ-02 | 国内地图服务使用的加密坐标，俗称"火星坐标" |

在国内地图上直接使用 GPS 原始坐标会出现数百米偏移。地图 SDK 内部已处理坐标转换，因此使用其输出坐标即可保证点位准确。

### 6.6 跨应用通信原理

Android 应用之间通过 Intent 通信。当应用发送一个带特定协议（scheme）的隐式 Intent 时，系统会查找注册了该协议的 App 并启动。若设备上没有匹配的应用，系统会抛出异常，需要捕获后回退到其他方案。

### 6.7 ORM 与编译期校验

Room 是 Google 官方提供的 ORM 框架。开发者使用注解声明实体与查询语句，编译阶段由注解处理器检查 SQL 中的表名、字段名是否与实体一致，一旦写错会直接编译失败，而不是等到运行时才暴露；同时自动生成数据库实现代码，省去手写游标解析的样板代码。

### 6.8 聚合查询与 N+1 问题

N+1 查询是指在获取一个列表后，为列表中的每条记录单独执行一次关联查询，总共产生 1 + N 次查询。当列表有 20 条记录时，就需要执行 21 次查询，性能开销明显。

解决方式是使用连接查询与分组聚合，一次查询同时取回列表数据与关联统计信息，将查询次数降为 1 次。

### A.1 球面距离计算（DistanceUtil.kt）

```kotlin
object DistanceUtil {
    private const val EARTH_RADIUS = 6371000.0 // 地球平均半径（米）

    /**
     * Haversine 球面距离公式
     * 用于计算两个经纬度坐标之间的真实距离
     */
    fun haversineMeters(lat1: Double, lng1: Double, lat2: Double, lng2: Double): Double {
        val phi1 = Math.toRadians(lat1)
        val phi2 = Math.toRadians(lat2)
        val dPhi = Math.toRadians(lat2 - lat1)
        val dLambda = Math.toRadians(lng2 - lng1)

        val a = Math.sin(dPhi / 2).let { it * it } +
                Math.cos(phi1) * Math.cos(phi2) *
                Math.sin(dLambda / 2).let { it * it }
        val c = 2 * Math.atan2(Math.sqrt(a), Math.sqrt(1 - a))

        return EARTH_RADIUS * c
    }
}
```

### A.3 密码加盐哈希（PasswordUtil.kt）

```kotlin
object PasswordUtil {
    private const val SALT_LENGTH = 16

    /** 生成随机盐值 */
    fun generateSalt(): String {
        val bytes = ByteArray(SALT_LENGTH)
        SecureRandom().nextBytes(bytes)
        return Base64.encodeToString(bytes, Base64.NO_WRAP)
    }

    /** 计算加盐哈希 */
    fun hash(password: String, salt: String): String {
        val digest = MessageDigest.getInstance("SHA-256")
        val input = (salt + password).toByteArray(Charsets.UTF_8)
        return Base64.encodeToString(digest.digest(input), Base64.NO_WRAP)
    }

    /** 校验密码 */
    fun verify(password: String, salt: String, expectedHash: String): Boolean {
        return hash(password, salt) == expectedHash
    }
}
```

### A.4 数据仓库流水线（ToiletRepository.kt 节选）

```kotlin
object ToiletRepository {
    /**
     * 完整的周边厕所数据流水线：
     * 定位 → 逆地理 → POI 检索 → 距离排序 → 缓存 → 聚合
     */
    suspend fun loadNearbyToilets(context: Context, lat: Double, lng: Double): List<ToiletItem> {
        // 1. 圆形范围检索
        val pois = searchPoi(context, lat, lng, radius = 3000)

        // 2. 转换为业务对象并计算真实距离
        val items = pois.map { poi ->
            ToiletItem(
                id = poi.poiId,
                name = poi.title,
                address = poi.snippet,
                lat = poi.latLonPoint.latitude,
                lng = poi.latLonPoint.longitude,
                distance = DistanceUtil.haversineMeters(
                    lat, lng, poi.latLonPoint.latitude, poi.latLonPoint.longitude
                )
            )
        }.sortedBy { it.distance } // 3. 按真实距离升序

        // 4. 写入数据库缓存
        cacheToDatabase(context, items)

        // 5. 聚合评价统计后返回
        return attachReviewStats(context, items)
    }
}
```

/**
 * 唤起步行导航，未安装高德地图时回退到网页版
 */
private fun navigateOnFoot(lat: Double, lng: Double, name: String) {
    val uri = Uri.parse("amapuri://route/plan/?dlat=$lat&dlon=$lng&dname=$name&t=2")
    val intent = Intent(Intent.ACTION_VIEW, uri).apply {
        addFlags(Intent.FLAG_ACTIVITY_NEW_TASK)
    }
    try {
        startActivity(intent)
    } catch (e: ActivityNotFoundException) {
        // 回退到网页版导航
        val webUri = Uri.parse("https://uri.amap.com/navigation?to=$lng,$lat,$name&mode=walk")
        startActivity(Intent(Intent.ACTION_VIEW, webUri))
    }
}
