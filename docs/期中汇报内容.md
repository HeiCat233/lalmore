## 一、项目概述

### 1.1 选题背景

「找厕所」是每个人都会遇到的高频刚需。在熟悉的地方不成问题，但一旦身处陌生街区、旅游景区或大型商场，想要快速找到一处可用、干净的公共厕所，往往并不顺利。

结合日常使用可以发现几个普遍问题：

1. **搜索结果杂乱**。地图搜索"厕所"时，结果中常混入商场内部点位、已关闭点位和名称相近的无关地点，需要逐个判断。
2. **排序不符合真实距离**。地图默认按综合权重排序，"最近的"未必排在最前。
3. **缺少质量信息**。有没有纸、洗手台是公共还是独立、是否有人清理，这些关键信息没有任何平台收录。
4. **流程割裂**。从"搜到"到"走到"需要在地图、点评等多个应用间切换，急迫场景下体验差。

### 1.2 项目目标

开发一款轻量的 Android 应用，让用户能够：

- **搜得到**：快速找到附近真实可用的公共厕所；
- **看得懂**：通过结构化指标和用户评价，提前判断厕所条件；
- **走得到**：从详情页一键唤起步行导航，直接走到目的地。

### 1.3 选题意义

本选题场景虽小，但链路完整，能够覆盖移动应用开发的主要知识点：定位与地图、网络检索、本地数据存储、多界面架构、用户体系与跨应用通信，是一个适合课程大作业的题目。

## 二、需求分析

### 2.1 目标用户

游客、通勤的上班族与学生、户外工作者、带小孩的家庭。他们的共同特点是：需求突发、时间紧迫、对位置和可用性要求高。

### 2.2 功能需求

| 编号 | 功能模块 | 功能描述 |
|---|---|---|
| F1 | 用户定位 | 获取当前位置并显示所在城市与区县 |
| F2 | 周边搜索 | 检索当前位置 3 公里内的公共厕所 |
| F3 | 距离排序 | 按球面距离由近到远排序 |
| F4 | 地图展示 | 蓝点定位与 Marker 标注，支持点选 |
| F5 | 厕所详情 | 展示基础信息、结构化指标与用户评价 |
| F6 | 用户账号 | 注册、登录与登录态保持 |
| F7 | 发布评价 | 星级、标签、三项指标与文字内容 |
| F8 | 排行榜 | 好评榜与热评榜 |
| F9 | 步行导航 | 深链唤起导航，支持网页回退 |

### 2.3 非功能需求

| 类别 | 要求 |
|---|---|
| 易用性 | 主流程不超过 3 步，界面层次清晰 |
| 稳定性 | 权限拒绝、断网、未安装第三方地图等异常不崩溃 |
| 性能 | 列表差量刷新，冷启动优先展示本地缓存 |
| 安全性 | 用户密码不以明文存储 |
| 兼容性 | 最低支持 Android 8.0，覆盖主流机型 |

## 三、系统设计

### 3.1 设计原则

本项目遵循"**使用成熟框架、不重复造轮子**"的原则：地图与定位直接采用高德 SDK，数据持久化采用官方 Room 框架，界面采用 Material 组件库，把开发精力集中在业务整合与工程质量上。

### 3.2 技术选型

| 层次 | 选型 | 选择理由 |
|---|---|---|
| 开发语言 | Kotlin | Google 官方首推，语法简洁、空安全 |
| 开发工具 | Android Studio | Android 官方 IDE |
| 构建工具 | Gradle + AGP | 官方构建体系，依赖管理方便 |
| 界面体系 | View + ViewBinding + Material 3 | 组件成熟、资料丰富，适合课程项目 |
| 地图定位 | 高德地图 Android SDK | 定位、地图、POI 检索、逆地理一体化 |
| 本地存储 | Room（SQLite） | 官方 ORM，编译期校验 SQL |
| 轻量存储 | SharedPreferences | 保存登录态、最近定位等键值数据 |
| 异步处理 | Kotlin 协程 | 避免数据库与网络操作阻塞主线程 |
| 版本管理 | Git + GitHub | 满足团队协同考核要求 |

### 3.3 系统总体结构

系统采用三层结构：

```
界面层（Fragment / Activity / Adapter）
        ↓
数据仓库层（ToiletRepository 统一数据出口）
        ↓
数据层（Room 数据库 / 高德 SDK / SharedPreferences）
```

- **界面层**：只负责页面展示与用户交互；
- **数据仓库层**：统一封装定位、检索、排序、缓存、聚合等流程，供各页面共用；
- **数据层**：负责数据持久化与外部服务调用。

这样设计的好处是：数据来源变化时只需修改仓库层，界面层无需改动，也方便两人分工。

### 3.4 数据存储方案（简述）

采用"数据库 + 文件"两级存储：

- **Room 数据库**：保存厕所信息、用户评价、账号信息三类结构化数据；
- **SharedPreferences 文件**：保存登录状态、最近定位、搜索历史等轻量数据。

厕所记录的主键直接复用高德 POI 的唯一标识，保证地图点位与数据库记录一一对应。

### 3.5 地图与定位方案（简述）

- 使用高德混合定位获取当前经纬度；
- 以用户位置为圆心，检索 3 公里内的"公共厕所"；
- 对结果重新计算球面距离并按由近到远排序；
- 在地图上以 Marker 标注，点击可跳转详情；
- 详情页一键唤起步行导航，未安装高德时回退网页版。

## 四、数据库设计

数据库采用 Room 框架，计划包含三张表，另用 SharedPreferences 文件保存轻量数据。

### 4.1 表结构设计

**users（用户表）**

| 字段 | 说明 |
|---|---|
| id | 主键，自增 |
| username | 用户名，唯一索引 |
| passwordHash | 密码哈希值 |
| salt | 随机盐值 |
| nickname | 昵称 |
| createdAt | 注册时间 |

**toilets（厕所表）**

| 字段 | 说明 |
|---|---|
| id | 主键，复用高德 POI 唯一标识 |
| name | 厕所名称 |
| address | 详细地址 |
| lat / lng | 经纬度 |
| createdAt | 入库时间 |

**reviews（评价表）**

| 字段 | 说明 |
|---|---|
| id | 主键，自增 |
| toiletId | 外键，关联厕所 |
| userId | 外键，关联用户 |
| userName | 发布者昵称 |
| rating | 星级 1~5 |
| content | 评价内容 |
| tags | 标签，逗号分隔 |
| paperStatus / sinkType / cleaned | 三项结构化指标 |
| createdAt | 发布时间 |

### 4.2 表间关系

```
users 1 ──────< N reviews N >────── 1 toilets
```

一个用户可以发布多条评价，一个厕所有多条评价，评价通过两个外键分别关联厕所与用户。

### 4.3 设计要点

1. **主键复用**：厕所表主键直接采用高德 POI 唯一标识，地图点位与数据库记录一一对应；
2. **两级存储**：结构化数据进数据库，登录态、最近定位等轻量数据进文件，各取所长；
3. **安全存储**：密码采用"随机盐 + 哈希"方式，不保存明文。

## 五、界面设计

### 5.1 设计思路

界面借鉴大众点评的信息架构，采用蓝绿品牌色系，在保证信息密度的同时兼顾美观。

### 5.2 主要页面

| 页面 | 设计要点 |
|---|---|
| 首页 | 渐变头部 + 定位搜索区 + 快捷入口 + 厕所信息流卡片 |
| 地图页 | 全屏地图，蓝点定位 + Marker 标注 |
| 详情页 | 头图 + 基础信息卡 + 三项指标卡 + 评价列表 |
| 榜单页 | 好评榜与热评榜，前三名配奖牌标识 |
| 我的页 | 账号信息、我的评价、演示数据入口 |
| 登录页 | 登录与注册双模式切换 |

### 5.3 设计特色

在厕所详情页设计**三格结构化指标卡**，展示厕纸供应、洗手台类型、清理除味三项信息，并给出所有评价者的统计结果，让用户在出发前就能判断厕所的实际条件，这是本项目的界面特色。
